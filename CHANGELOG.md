# Changelog

All notable changes to `qasight` (named Testosterone and `testo-core` until 1.5.0) will be documented in this file.

This project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

---

## [Unreleased]

### Added
- Set QASight up without a terminal: commit the one-time `qasight-setup.yml` workflow from Getting Started (its button opens GitHub's editor with the file filled in) and the Action's new `setup: "true"` mode runs `qasight init --scan --attach --pr` and opens the setup pull request. When a pull request can't be opened (no `gh`, or a token that may not), `qasight init --pr` prints the GitHub link that opens it in one click
- `qasight init --attach` adds QASight to the GitHub workflows that already run your tests instead of writing a second workflow that runs them again: the test command gets a result-file flag (pytest, Jest, Vitest, npm/pnpm/yarn scripts, dotnet test, RSpec, PHPUnit; Maven and Gradle need none), each job gets one QASight step after its last test step that records those files, and a `permissions:` block gets `pull-requests: write`. Edited as text, so comments and formatting stay; `--dry-run` shows the diff, and commands it can't extend safely are listed, not guessed
- `qasight run -- <command>` runs any test command and records what it ran, with no `qasight.yaml`: it recognises pytest, Jest, Vitest, Playwright, `go test`, `dotnet test`, Maven, Gradle, RSpec and PHPUnit (also through `npx`, `uv run`, `python -m` and npm/pnpm/yarn scripts), adds the flag that writes a result file, keeps the command's output and exit code, and records unknown commands from the result files they wrote
- `qasight ingest --from-github` fills the history from past GitHub Actions runs: it downloads each run's artifacts with the GitHub CLI, records the result files in them as one run each (commit, branch, CI run id) dated when it ran, and skips runs already recorded. `--runs`, `--workflow` and `--branch` narrow it
- `qasight init --scan --per-package` writes one cycle per monorepo package, each triggered by changes to its folder, so `qasight run --cycle all` (and the generated GitHub workflow) runs only the packages a branch touched
- A stage's `serve: {command, url, timeout_s}` starts the app its tests need, waits until the URL answers and stops it after the stage, so end-to-end suites run with `qasight run` alone. `qasight init` now adds Cypress when it finds a `baseUrl` in `cypress.config.*` and a start, dev, preview or serve script, with `serve:` set up to start the app
- `npx qasight ...` for projects without Python: a small npm package (`integrations/npm-qasight/`) runs the CLI through uv and installs uv into its own cache when there is none. Published by hand with `publish-npm-qasight.yml`
- Release scorecard: `qasight scorecard scan` runs the repo review tools (Bandit, Semgrep, gitleaks, Flawfinder, OWASP ZAP, pip-audit, npm audit, Trivy, OpenSSF Scorecard, zizmor, Ruff, Schemathesis, Lighthouse, axe, k6) on any folder or git URL (`qasight scorecard scan https://github.com/torvalds/linux`), scores each 0-100 for the project's version, rolls them up by category and compares the version with the one before. `qasight scorecard import` records a report you ran yourself (coverage, mutmut or Stryker, Locust, any SARIF or JUnit file), `qasight scorecard show --min-score/--min-tool/--no-drop` is the release gate and writes a Markdown summary, and `qasight scorecard tools` switches tools on and off. A new Scorecard page shows the score, the change since the last version, a bar per version, every tool with its logo (where the tool has one) and an on/off switch, and a form to scan a repository. `release-gate.yml` scores the last release and the commit. API under `/api/v1/scorecard`. See `docs/Specs & ADRs/Release Scorecard - 2026-11-12.md`
- Release scorecard: the scorecard shows how many of the tools that fit the repository ran and caps the grade at C when fewer than half did; gitleaks leaves out test and fixture files, counts each secret once and ranks it by rule; a failed tool says why; `scorecard-ignore.yml` (or `--ignore`) accepts known false positives; each tool is listed once under "Not run"; `scan`, `import` and `show` print the history database they use
- Release gate: before a release, `release-gate.yml` runs Schemathesis, OWASP ZAP and a load test against a running API, Lighthouse CI on the demo site, fuzzing of every report importer and mutation testing, and the PyPI publish stops without a pass. Every pull request now also runs gitleaks, Bandit, pip-audit and `npm audit`. See `docs/Specs & ADRs/Release Gate - 2026-11-12.md`
- Release scorecard on MegaLinter: when Docker is available, `qasight scorecard scan` runs MegaLinter on the repository (any of its 50+ languages) and scores each linter it ran; Bandit, Semgrep, gitleaks and the other built-in scanners it covers run only as a fallback. Security and supply chain are rated by the worst finding (like SonarQube), code quality by issues per 1,000 source lines (like Codacy); tests, vendored and generated code and docs don't count; linters that repeat the project's own choice on default rules are shown but not scored. Each tool shows its new findings since the previous version, and `--no-new` fails the gate on a new high or critical one. `--megalinter-image` picks the image. See `docs/Specs & ADRs/Scorecard on MegaLinter - 2026-11-12.md`
- A CI job that builds a git tag records the tag as the run's release, and a CI run with no environment gets the runner's OS (`os=linux`), so the Releases page and an OS matrix work with no setup. `TESTO_AUTO_METADATA=0` turns it off.
- Single sign-on for the team server with any OpenID Connect provider (Google Workspace, Microsoft Entra ID, Okta, Keycloak, ...): with `TESTO_AUTH=accounts`, set `TESTO_OIDC_ISSUER`, `TESTO_OIDC_CLIENT_ID` and `TESTO_OIDC_CLIENT_SECRET` and `/login` shows a "Sign in with SSO" button. The first sign-in creates an account named after the verified email (`TESTO_OIDC_DEFAULT_ROLE`, default `viewer`); `TESTO_OIDC_ALLOWED_DOMAINS` limits it to your email domains. The `api` extra now installs `pyjwt[crypto]`
- One-click hosting: a Deploy to Render button (`render.yaml`: the server image, Postgres, a disk and a generated token) and a Helm chart in `deploy/helm/qasight`. `DATABASE_URL` accepts the bare `postgres://` and `postgresql://` URLs that hosts hand out
- Live results: `pytest --qasight-server` sends each result to the team server while the tests run, and the dashboard shows the session under **Running now** with its progress and first failures until the report is uploaded. `--qasight-no-live` / `TESTO_LIVE=0` turns it off. API: `GET/POST /api/v1/live-runs`, `POST /api/v1/live-runs/{id}/results` and `/finish`
- Scorecard in pull requests: the GitHub Action's `scorecard` input (`true` after the tests, `only` instead) scores the repository, writes the scorecard to the job summary and one pull request comment, and gates with `scorecard-min-score` and `scorecard-no-new`. `qasight scorecard show --format sarif|html|svg` writes SARIF for GitHub code scanning (the Action's `scorecard_sarif` output), a self-contained HTML page and a README badge; a team server serves the badge at `/api/v1/scorecard/badge.svg` (and `badge.json` for shields.io) and SARIF at `/api/v1/scorecard/sarif`
- Every release carries CycloneDX SBOMs (`qasight-<version>-python.cdx.json` and `-ui.cdx.json` on the GitHub release), and the Docker images carry signed SLSA provenance and an SPDX SBOM. The web UI is checked against WCAG 2.1 AA with axe on every page in the frontend tests. See `docs/Specs & ADRs/Standards Compliance - 2026-11-12.md`
- A [stability and deprecation policy](docs/Processes%20&%20Guides/Stability%20and%20Deprecation%20Policy.md): what stays stable in 1.x and how much warning a change gets
- `qasight ci publish`: the after-run step for any CI. It writes the summary, comments on the GitHub pull request or GitLab merge request (`TESTO_GITLAB_TOKEN`) and edits it on later runs, adds GitHub annotations and sends the Slack or Teams alert. The GitHub Action and the GitLab, Jenkins and CircleCI templates from `qasight init` use it, and the Action's `flaky-issues` input now uses the run's own issue sync, which also closes fixed issues. It skips a Slack or Teams channel that `qasight.yaml` already has a reporter for, so a project that set up both gets each alert once.
- The team server sends the weekly or daily digest and the manager report email on its own schedule (`TESTO_SCHEDULE_DIGEST`, `TESTO_SCHEDULE_TO`, `TESTO_SCHEDULE_HOUR`), with no cron job.
- The run page suggests a cause for failures with a well-known message (a refused connection, DNS, a full disk, a missing module or fixture...), and one click accepts it.
- `integrations/github-action/action.yml` is generated from the root `action.yml` by `scripts/sync_action_copy.py`.

### Security
- The API sends `Referrer-Policy: strict-origin-when-cross-origin` on every response and `Strict-Transport-Security` over HTTPS (OWASP ASVS level 1)
- Uploaded and stage JUnit, TRX, Robot Framework and coverage XML, and the XML reports `qasight scorecard` reads, are parsed with `defusedxml`: a file that declares entities is reported as unreadable instead of being expanded. `defusedxml` is a new dependency
- GitHub Actions hardening: every third-party action is pinned to a commit SHA, checkouts no longer keep the job token unless the workflow pushes, the PyPI release build no longer restores the npm cache, and branch names reach shell scripts through `env:`. CI now runs zizmor on the workflows, and a weekly OpenSSF Scorecard workflow reports to code scanning (results are not published). See `docs/Specs & ADRs/External Audit Tools - 2026-11-11.md`
- The web UI sends a full Content Security Policy (everything from its own origin, no plugins, no foreign forms). The Plus Jakarta Sans font is bundled with the app instead of loaded from Google Fonts

### Fixed
- A resource lease with a TTL under 3 seconds is now heartbeated three times per TTL instead of once a second, so a busy machine no longer loses it
- The weekly digest and the run page's failing tests judge flakiness with the Flaky page's rule (per branch, commit and environment); the digest listed a pull request that broke and fixed a test as newly flaky.
- A cycle's `trigger.paths` pattern with `**` now spans folders: `api/**` matches `api/src/app.py` and `**/*.py` matches a top-level file (before, `**` matched a single folder)
- API: a `config_path` or `artifacts_root` that is not a usable path (a NUL byte, an unknown `~user`) answers 400 instead of 500. Found by the first full run of the release gate.
- The API answers a dashboard `limit` / `recent_limit` too large for the database, and a request body it cannot parse, with a 422 instead of a 500 (found by Schemathesis)
- Needs attention and project health count a run marked failed as red even when its exit code is 0
- A JSON report with a wrong-typed field says which format it looked like and that a field is missing or has an unexpected type, instead of a bare `TypeError`
- The single-file HTML report (`qasight report --html`) works again with the on-demand page loading
- Accessibility (found by axe): Compare and the test page keep their heading while loading or empty, the report's small print has 4.8:1 contrast instead of 2.6:1, and its wide tables scroll from the keyboard

### Performance
- The API keeps the manager report, Needs attention and project health in memory until a run is added, finishes or is deleted (`TESTO_READ_CACHE_S`, default 60 s, `0` off). With 50 users the API answers 5.7 times as many requests, median 0.16 s instead of 2.6 s
- The web UI loads each page other than the dashboard on demand (the first download is 344 kB instead of 610 kB), and the dashboard no longer jumps while the demo notice and the first data load. The page has a meta description

## [1.6.0] - 2026-11-05

### Renamed
- Testosterone is now **QASight**. The package is `qasight` (`pip install qasight`), the command is `qasight`, the Python modules are `qasight` and `qasight_api`, the config file is `qasight.yaml`, the pytest flags are `--qasight...`, plugin entry points are `qasight.frameworks` / `qasight.reporters`, and the Docker images are `qasight-runner`, `qasight-server` and `qasight-runner-service`. Everything from before keeps working: the `testo` command, `testosterone.yaml` / `testosterone.yml` and `[tool.testosterone]`, `pytest --testo...`, the `testo.*` entry point groups, and every `TESTO_*` setting (which `QASIGHT_*` can now also set). `testo-core` is still released at the same version: it installs `qasight` and keeps `import testo_core` / `import testo_api` working with a deprecation warning, so `pip install -U testo-core` upgrades too. Files the tool writes keep their names (`.testo/`, `testo_history.db`, `testo-summary.md`), and the team server's Postgres user and database stay `testo`. See [Rename to QASight](docs/Specs%20&%20ADRs/Rename%20to%20QASight%20-%202026-11-04.md)

### Added
- Storage limits: report archives (`qasight report list`) now follow `history.retention` like runs, and `qasight report delete --id` removes them by hand. `TESTO_RETENTION_DAYS` and `TESTO_RETENTION_RUNS_PER_CYCLE` set (or override) the limits without a `qasight.yaml`, so the Docker team server can be limited by its environment. `history.max_file_mb` / `TESTO_HISTORY_MAX_FILE_MB` leaves big files (videos, traces) out of a run's history copy and report archive. `qasight server init` sets 180 days and 100 MB for new servers; existing servers keep everything until a limit is set
- Storage visibility: the Runs page shows how many runs there are, the database and file sizes, report archives and free disk, and warns when the disk is getting full (`GET /api/v1/storage`, `TESTO_LOW_DISK_PCT`). `/api/v1/health/ready` has a `disk` check, and `qasight doctor` prints `Disk` and `History size` rows
- A run that dies mid-way (`kill -9`, out of memory, a crashed server) is recorded as a failed run ("stopped without finishing") when its cycle next runs or the API server starts, instead of leaving no trace
- Token rotation: `TESTO_API_TOKEN_PREVIOUS` is accepted next to a new `TESTO_API_TOKEN` while CI secrets are updated, and `TESTO_SESSION_KEY` signs sign-in cookies instead of the token so a new token keeps people signed in. `qasight server init` generates a session key
- `qasight export-site` writes the web UI and recent runs as a read-only static site for GitHub Pages or any file host, and the GitHub Action's `static-site: "true"` uploads it for an `actions/deploy-pages` job. The UI bundled in the wheel now works under any path, so one build serves `qasight ui` and the site. The `api` extra adds `httpx`
- Delete chosen runs: the Runs page has **Select runs**, then a checkbox per finished run and **Delete selected** (with a confirm). The CLI does it with `qasight clean --history --run ID` (repeatable), and the API with `POST /api/v1/runs:delete` (`{"run_ids": [...]}`; an admin's call in accounts mode). Like retention, a run's row, its per-test rows and its report copy go together, and a running run is skipped
- Stop a run: the cycle page and Quick run show a **Stop** button while a run is going (press again to kill stages that ignore the first stop). Only that run's stages are stopped, the rest of its stages are skipped, and it is still recorded, as stopped. A queued run is dropped before it starts. API: `POST /api/v1/cycle-executions/{id}/cancel`; the execution's status becomes `cancelled`
- The Runs page says how long runs are kept (`history.retention`) and the default stage time limit (`timeout_s`), from `GET /api/v1/run-settings`
- Report: where failures concentrate (the few tests behind most failures, the most repeated errors), retry rate and line coverage by day, tests with unstable timing, when failures happen (by hour, weekday and environment, with a sentence when one fails far more often), and tests that caught real bugs against tests that only raised false alarms. The test page shows each test's slowest-runs time and flags unstable timing
- Report: a By team table (each CODEOWNERS owner or `owner` label: tests, failing, open failures and the oldest, time to fix, flaky tests and their cost) and the suite's size against the period before with the tests added and removed, tests skipped in every run, and slow tests that never failed
- Report: why runs were red and what flakiness costs. The `/report` page counts the period's red runs by cause (real bug, bug in the test, environment, flaky tests, crash or setup, not marked yet) from the causes marked on failures and the flaky classification, with the share that was noise, and shows the CI minutes flaky tests cost (their retries plus the red runs only they caused), the branches they held up and the most costly tests. The cycle page's flaky tests show their cost and are sorted most costly first
- Report and dashboard: how long failing tests stay red and what the suite costs. The `/report` page has a Speed and stability section (median time to fix failing tests, open failures by age with the oldest listed, the share of the period the default branch was red and its longest red spell, CI minutes, first-try green rate of pull request commits), a Suite time by day chart, and a per-cycle table with suite time, slowest 10% and the stage that grew most. The dashboard has a Last 7 days card with the same numbers (`GET /api/v1/dashboard/delivery`). Flaky tests and reruns of the same commit are left out of time to fix
- Issues with red tests: the cycle page's new "Issues" card groups tests by the issue they point at (issue links and `issue` labels from N1's labels and links) and lists the issues with a failing test first, with links to the tracker and to the failing tests. API: `GET /api/v1/analytics/issues?cycle=`
- Releases: record the release a run tests with `qasight run --release 2.3` (also `qasight ingest --release`, `TESTO_RELEASE`, and the GitHub Action's `release` input). A new Releases page lists every release with its pass rate, and each release's page shows its cycles, failing tests (with the ones new since the release before), flaky tests and what it fixed. API: `GET /api/v1/releases` and `GET /api/v1/releases/{release}`; `release` on run items and the run detail
- Run a chosen set of tests: `qasight run --test NAME` (repeatable) and `qasight run --rerun-failed RUN_ID`, with pytest node ids or `-k`, Playwright `--grep` and Behave `--name`, plus Allure's test plan file (`ALLURE_TESTPLAN_PATH`) for other runners. The run page has "Run these tests again", and the cycle page's label filter has "Run these". API: `tests` and `rerun_failed` on `POST /api/v1/cycles/{cycle}/executions`
- Environments: `qasight run --env browser=firefox --env os=linux` (also `qasight ingest`, the `TESTO_ENV` variable, Allure's `environment.properties`, and the GitHub Action's new `environment` input) records what a run tested on. Flaky detection and failing streaks keep environments apart, so a test that always fails on one browser is a failure there, not flaky. The run page and runs list show the environment, and the test page has a "By environment" card ("Fails only on browser=firefox")
- Test labels and issue links: each test keeps what it is about (feature, story, epic, severity, owner, tags and custom labels) and its issue links, read from Allure results, allure-pytest markers, Playwright tags and annotations, Behave tags and a JUnit test case's own `<properties>` (`record_property("feature", "Checkout")`). The run page and the test page show them as chips; the cycle page has a "By label" card ("Checkout: 12 tests, 3 failing") and filters its tests with `?label=`. API: `GET /api/v1/analytics/labels?cycle=`, and `label=` on `GET /api/v1/analytics/tests`. Migration `0006` adds the `labels` and `links` columns to `test_result`, run automatically
- `qasight export pdf|pptx|xlsx|png|html|csv|json` writes the manager report as a file, and the Report page's Download menu gets the same files from the server (`GET /api/v1/report/export`). PowerPoint has six slides with native, editable charts and tables; Excel has Summary, Trend (with a chart), Cycles, Tests and Findings sheets; HTML is one file that opens offline; PDF and PNG are drawn by headless Chromium. PDF, PNG, PowerPoint and Excel need the new `export` extra (`pip install 'qasight[export]'`, then `playwright install chromium` for PDF and PNG). The team server image includes PowerPoint and Excel, and PDF with `--build-arg TESTO_REPORT_PDF=1`
- `qasight notify --digest week --to email` emails the manager report over SMTP (`TESTO_SMTP_*`): a summary in the body and the report attached (`--attach pdf|pptx|xlsx|html|png|none`, recipients from `--email-to` or `TESTO_REPORT_EMAIL_TO`)
- A Report page (`/report`) for managers: test health score, pass rate and green builds against the period before, a short written summary, pass-rate and runs-per-day charts, a table per cycle, and what is failing, turned flaky, got fixed or got slower, for the last day, 7, 30 or 90 days and all cycles or one. "Save as PDF" prints it as a clean white document (any page now prints without the app's navigation and dark background). The data is `GET /api/v1/report`
- Every card in the UI has a Copy menu: copy as text, copy as a table that pastes into email, Slack, Confluence, Notion or a spreadsheet, download CSV, copy or download a chart as a PNG, and a link to the card. The run page has "Copy summary", the run as Markdown (`GET /api/v1/runs/{id}/markdown`, the `qasight report markdown` text)
- AI failure summaries can read the failing test's own source: an opt-in switch on the AI settings page ("Let the AI read the failing test's source"), `qasight ai setup --share-test-source` or `TESTO_AI_SHARE_TEST_SOURCE=1`. Off by default. It sends only the test's definition and a few lines around the failing line, from files inside the run's checkout, at most 3 files and 4,000 characters, redacted, never `.env` files, keys or certificates. With a cloud provider the page warns that the excerpt goes to it; with Claude Code it goes through your own login. Run Details says when a summary read test source
- `qasight plugins new NAME` writes a working plugin package (framework adapter, reporter, entry points, a cycle and a test) to start a runner or reporter from
- `qasight server init [--domain testo.example.com] [--admin NAME]` writes a team server's `docker-compose.yml` and a private `.env` with a generated token; `--domain` adds Caddy for automatic HTTPS, `--admin` turns on accounts. A server with `TESTO_AUTH=accounts` and no accounts creates `TESTO_ADMIN_USER` / `TESTO_ADMIN_PASSWORD` as its first admin when it starts
- `qasight doctor` and the web UI's sidebar say when a newer qasight is on PyPI (asked at most once a day, never in CI, off with `TESTO_NO_UPDATE_CHECK=1`); new `GET /api/v1/version`
- A missing optional dependency prints one line naming the extra to install (`pip install 'qasight[api]'`), or a reinstall for a broken environment, instead of a traceback; `qasight ui` without the `api` extra offers to install it when run in a terminal
- `qasight ui --from-github [--repo owner/name] [--run-id ID]` opens the UI on the history the GitHub Action keeps in CI, so nobody needs a server to browse it. The Action now also uploads its cached history as a `testo-history-*` artifact (kept 7 days, `history-artifact: false` turns it off), which this downloads with the GitHub CLI
- `TESTO_QUARANTINE_AUTO=0.3` quarantines, after each recorded run, the tests that are flaky at that flip rate or more and failed in that run (never ones that always fail), and the pull request comment lists them. Off by default. Escaped names (`test_x[[]1]`) let parametrized tests be quarantined and released like any exact name
- `qasight quarantine add` on a local SQLite history also prints the `quarantine:` lines for `qasight.yaml`, since CI never sees this machine's list
- `qasight mcp install [--client claude-code|cursor|vscode|claude-desktop]` adds `qasight mcp` to the agent's MCP config file, keeping the other servers in it
- Team server: the compose file's `backup` service runs `qasight backup` daily and keeps the newest 7 (`TESTO_BACKUP_KEEP`, `TESTO_BACKUP_EVERY_S`)
- `qasight ai setup` turns on AI failure summaries with a provider this machine already has (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY` for Gemini's free tier, or the Claude Code CLI) and saves it where the UI's AI settings page reads it; `qasight ai status` and `qasight ai summary` (the latest failed run's summary). In CI, `TESTO_AI_PROVIDER` and friends set the provider from the environment. `qasight report markdown --ai` and the Action's `ai-summary: "true"` add the summary to the job summary and pull request comment
- Pull requests from forks get the comment too: the Action's `comment-artifact` input uploads it as an artifact instead of posting it with the fork's read-only token, and `post-comments-from` posts it from a `workflow_run` workflow (no fork code checked out, marker-prefixed files only, pull request found by the tested commit). `qasight init --forks` writes both workflows
- GitHub Action: `server-url` and `server-token` also upload each recorded run to a team server (the result files, or each stage's results for a cycle it ran), and the job summary says when the Actions cache had no earlier history to compare with. `qasight init --server URL` writes those inputs and, with `gh` and `$TESTO_API_TOKEN`, stores the secret
- `qasight init --pr` commits the files it wrote on a new branch, pushes it and opens a pull request with the GitHub CLI (or prints the commands left without it); `qasight init --dependabot` also writes `.github/dependabot.yml` for weekly GitHub Actions updates
- `qasight try --run` runs the project's tests first, the way the CI file `qasight init` writes does, then previews the comment
- `qasight init --scan` sets up a monorepo: it looks in every project folder and writes a stage per runner per folder (with `target_repo`), skipping folders an outer stage already covers, then shows the stages and asks before writing (`--yes` skips the question). `--check` asks each runner to list its tests without running them (`pytest --collect-only`, `jest --listTests`, `go test -list`, ...) and leaves out stages with none
- Ask about your tests: an Ask page where you type a question ("what broke, and is it new?", "which tests got slower?") and your AI provider answers from the recorded runs (results, failure messages, flaky and slow tests, test names, never source code), with follow-up questions in the same conversation. New endpoint `POST /api/v1/ask`; nothing is stored on the server

### Security
- Secrets are hidden in a run's stored results and logs before it is recorded (API keys, cloud and GitHub/GitLab/Slack tokens, JWTs, bearer tokens, `password=`, credentials in URLs, private keys), for `qasight run`, `qasight ingest`, uploads and `pytest --qasight`. Add patterns with `TESTO_REDACT_PATTERNS` (one regular expression per line); `TESTO_REDACT=0` turns it off
- With `TESTO_RUNNER=container`, a `per: stage` resource pool with `on_take` / `on_check` / `on_release` is refused: those hooks ran in the API server's own process, outside the stage's container, so a runner could run commands on the server. `per: test` hooks keep working (they run inside the container)
- The GitHub Action pins `actions/setup-python` to a commit SHA, and the publish and commitlint workflows pin their third-party actions the same way
- Accounts: removing a user and adding the same name again no longer revives the old person's session cookies (cookies now carry the account's creation time). Existing account sessions sign in again once after the upgrade
- Failure evidence redaction (before storage and before an AI provider sees it) now also catches GitHub, GitLab, npm, Slack, AWS and Google tokens, JWTs, `Basic` credentials, passwords in URLs (`scheme://user:***@host`), `password=` values, quoted JSON keys and private key blocks, and masks `password`, `DATABASE_URL`, `privateKey` and `cookie` fields
- AI provider requests no longer follow HTTP redirects, which resent the `Authorization` / `x-api-key` header to the redirect's host
- With `TESTO_RUNNER=container`, `${env:...}` in a stage's `args` or `env:` no longer reads the server's own secrets (`TESTO_*`, `DATABASE_URL`, `POSTGRES_*`, `*_API_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD`, `*_DB_URL`). Before, a runner could copy `TESTO_API_TOKEN` (the admin credential) into a throwaway container with `${env:TESTO_API_TOKEN}`
- The development `docker-compose.yml` publishes Postgres (default password `admin`) on `127.0.0.1` only, not on every network interface
- A token-less API (the local default and `qasight ui`) answers only requests addressed to `localhost`, `127.0.0.1` or `::1`, so a web page using DNS rebinding can no longer read runs, logs and reports from it. `TESTO_ALLOWED_HOSTS` adds names; a token or `TESTO_ALLOW_UNAUTHENTICATED=1` lifts the check
- `TESTO_CORS_ORIGINS=*` no longer lets any web page start runs on a token-less API; `*` waives the Origin check only when a token is required anyway
- Uploaded Allure attachments can no longer run script on the API's origin: `qasight ingest` stores each one under a `<uuid>-attachment` name, and every file under a raw `allure-results/` folder is served in a CSP sandbox. Before, an upload with an attachment named `page.html` was served as a normal page
- GitHub Action: inputs reach its shell steps as environment variables instead of being pasted into the script, so a `"` or `$(...)` in an input (`cycle: ${{ github.head_ref }}`) can no longer run commands
- PR comment and job summary: a backtick in a test name (which in a fork's pull request its author controls) ended the code span, so `@user` mentions and HTML after it rendered live. Names are now fenced so nothing inside can close them, and stage, runner and branch cells are plain text. A cycle name with `-->` can no longer end the comment marker
